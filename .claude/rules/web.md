# Web (apps/web)

- Routes are files under `src/routes` (TanStack Router, file-based). `routeTree.gen.ts` is generated and committed. Route files export only `Route`; screens live in `src/screens/`. `_app.tsx` is the signed-in layout; `sign-in.tsx` is the only public route.
- Put anything shareable in the URL (which room, which filter, which vendor's panel is open: `/vendors?vendor=<id>`, OD-112; which estimate is being edited: `/jobs/<id>?estimate=<id>`, OD-119).
- Server state via TanStack Query through `@trpc/tanstack-react-query` (`useTRPC()` → `useQuery(trpc.x.y.queryOptions())`). One Supabase client (`src/lib/supabase.ts`, PKCE); the tRPC link attaches the access token. Zustand only for UI state that must outlive a route. No Redux, no context-as-store.
- Saves refresh through the shared lists in `lib/refresh.ts` (`useRefreshJobs`, `useRefreshPhases`, `useRefreshMoney`, `useRefreshShopping`), never a hand-picked set of `invalidateQueries`. Detail pages start all their queries from the route's `loader` (`lib/prefetch.ts`, not awaited, so the page isn't held back). Everything refetches only when who's signed in changes, not on the hourly token refresh (OD-115, Q136–Q137).
- Pictures in lists and tiles use `thumbUrl ?? url`: a 640px JPEG made in the browser at upload (`lib/thumbnail.ts`); the smallest tiles (a shopping row's picture, a room card's cover) use `tinyUrl ?? thumbUrl ?? url`, a 160px copy made at the same time (OD-141, Q208); the viewer and a room's cover band use the original. Admins make either copy for older pictures in Manage. Signed picture links are kept across refetches while under 45 minutes old (`lib/stable-links.ts`), so pictures don't download again (OD-115).
- Forms: react-hook-form + the shared Zod schema via `zodResolver` — the same schema the API validates with.
- Derived values (areas, totals, progress) come from the API, not computed in React.
- Tailwind v4 utilities in JSX. Extract a component when the same cluster appears three times. No CSS modules or styled-components.
- Phone and laptop are equal: every screen works at 375px wide and on a laptop. Touch targets at least 44px; nothing depends on a mouse.
- Roles on screen come only from `useMe()` (`role`, `canEdit`, `isAdmin`). A real admin can preview the app as an editor or viewer (OD-133): "View as" in the account menu and the phone's Menu panel (`components/view-as.tsx`), kept for the tab in sessionStorage (`lib/view-as.ts`), sent to the API as a header so it refuses what that role couldn't do, and shown by a bar across the top with "Back to admin". The switch and bar go by `isRealAdmin`/`realRole`, never the previewed role, and going back is local, so an admin can't be locked out.
- Vendors has no tab in the laptop top bar; it's reached from Jobs, so Jobs is marked current on /vendors (OD-112, Q126).
- The laptop top bar starts at 768px (`md:`); below that, the phone's bottom bar and Menu panel. Anything that sits above the bottom bar (toasts, the batch bar) switches at `md:` too (OD-111, Q125).
- Every page names the browser tab, most specific first ("Kitchen, Rooms, Reparo"): `PageHeader` does it from its title (`tabTitle` for a page inside a section), other pages render `PageTitle`. After moving to another page, focus goes to its `h1`. Unknown addresses show `NotHere` (in the shell) or `NotHerePage` (outside it); a page that breaks shows `PageError` (OD-111, Q123–Q124).
- Accessibility: semantic elements, a label on every input, keyboard-reachable actions, visible focus. Colour never carries meaning alone. "Skip to the page" is the first thing Tab reaches (`#main`). Layout grids use `grid-cols-[minmax(0,1fr)]` on a phone and data tables scroll inside themselves, so enlarged text wraps instead of pushing the page sideways; the phone breakpoint in JS (`useIsPhone`) is in rem like Tailwind's. The picture viewer keeps pinch-zoom and has Open full size (OD-142).
- Tests: Vitest, next to the code, for logic-bearing modules.
- Build: React and React DOM are their own chunk (`vite.config.ts` `codeSplitting`), so they stay cached across releases and the app's first chunk stays under Vite's 500 kB warning (OD-142).

## Design system: Plaster and tape

Decisions and reasons: Linear → *Design system* doc. Values: `src/index.css` (the only place colors, type sizes and radii are defined — never hard-code a hex, px font size or one-off radius in JSX). Visual reference: the canvas linked from that doc, section D.

**Tokens (Tailwind classes).** Use the semantic names, not raw palette colors (`bg-neutral-*`, `text-gray-*` etc. are out).
- Surfaces: `bg-background` (page), `bg-card` (panels, fields), `bg-inset` (recessed areas, picture placeholders), `bg-band` (heading strips inside a panel, like Shopping's rooms; OD-99), `bg-bar` (top/bottom bars).
- Text: `text-foreground`; `text-muted-foreground` for secondary text. Nothing lighter for readable text.
- Lines: `border-border` for dividers and panel edges; `border-input` for anything you interact with (fields, outline buttons, selects) — it's the 3:1 one.
- Actions: `bg-primary`/`text-primary-foreground` is the dark main button; `destructive` is brick red, for delete-type actions, negative money and errors (OD-84). `status-done` green is for Completed, for Saved, and for the Purchased position of a line's purchase switch; `destructive-tint` behind red text is the switch's Returned position (OD-132, Q192). Nothing else.
- Status: `status-idle`, `status-progress`, `status-done` (+ `-tint` backgrounds); awaiting review is `bg-tape text-tape-ink`.
- shadcn's `accent` is a **hover background**, never the tape yellow.

**Tape yellow (`tape`) is reserved** for: what needs someone (awaiting review, the attention count, Needs you), the mark on a tape where what's left starts, and the current-page marker in navigation (OD-138, Q203). Always a fill behind `text-tape-ink`, never text or an icon on a light background. Don't use it for buttons, links or decoration.

**Settled chips.** Paid in full, Chosen and Purchased use a neutral chip in lists (only the line's purchase switch is green/red, OD-132, Q193) (`bg-inset`, check icon), not the Completed green. Idle chips (Unstarted, Cancelled, Unpaid, To buy, Declined) carry a faint ring of their text color, because their tint equals the row hover color (OD-114, Q130, Q150).

**Colour and money.** Money is in the normal text color, with `tabular-nums`. Red (`text-destructive`) only when money goes negative or over budget. No green for "good" money; the Saved green is about the save, not the amount.

**Type.** Archivo (self-hosted). `h1`–`h3` get the narrow heading width from the base styles — use real heading elements rather than styling a `div`. Sizes: `text-4xl` 44, `text-3xl` 32, `text-2xl` 24, `text-xl` 20, `text-lg` 18 (a row's name, such as a shopping line or vendor; OD-114, Q135), `text-base` 16 (body), `text-sm` 14 (smallest). Nothing below 14px. Sentence case; no all-caps labels. On a dark surface (dark mode, or `.ink` in light mode) body text gets 0.01em tracking and 14px text weight 450, from base styles in `index.css` (OD-130, Q186). Explainer sentences under headings are kept only when they prevent a mistake or say something the heading doesn't, and then in one line (OD-130, Q185).

**Shape and depth.** `rounded-lg` (6px) on controls and chips, `rounded-xl` (10px) on panels. Separate sections with tone and a thin border, not a shadow on every card. Shadows only on things that float (menus, dialogs, the phone bottom bar), and only `shadow-float` / `shadow-knob` / `shadow-float-up` (the bottom bar), built from the `float-shadow` token so they show in dark mode; never Tailwind's own `shadow-sm`/`shadow-lg` (OD-142).

**The tape motif** is the one bold element: money and progress bars drawn as tape measure (ticks along the top, dark fill for spent/done, what's left as the pale plaster `tape-track` with a 4px yellow mark where it starts, so an untouched tape reads as empty; OD-138, Q203), drafting dimension lines for room sizes (a room's size is a small floor plan, `FloorPlan`: the room drawn to its proportions with length along the top, width down the side, area inside and the ceiling beside it, below on a phone; OD-128, Q180), the plan grid (`grid` token) only in empty states, picture placeholders and behind a room's outline. The budget tape splits its fill into spent (solid `tape-fill`) and planned (striped, `COMMITTED_STRIPES`); over budget the scale runs to the total, the budget's end is marked and labelled, and the overrun is red (`destructive`), with a matching legend swatch. Tapes are outlined (`tape-edge`: ink in light mode, grey in dark) and ticks use `tape-tick`; legends show what's left as `LEFT_SWATCH`. In dark mode `tape-fill` is a lighter grey, about 4:1 on the track and the page, so a full tape doesn't look empty (OD-109, OD-138). Don't add other decorative flourishes, and no monospace "technical" labels.

**Components.** shadcn/ui on Base UI, Nova style, in `src/components/ui/`; `cn` from `@/lib/utils`. Add a component when an issue needs it — the CLI (`pnpm exec shadcn add <name>`) or, if it can't reach the registry, by hand from shadcn's source with the source commit noted in the file. Then adapt it to these rules before use: Nova's defaults are compact (32px controls, 14px text, faint outline borders, a 50% focus ring), which break the 44px, 16px, 3:1 and focus rules here. Two- and three-way choices (By room/By store, Money in/out, purchase status, View as) are `SegmentedSwitch` (`components/segmented-switch.tsx`, look in `lib/switch.ts`): radios under a sliding knob with a `border-input` edge; Appearance is the one icon variant (OD-142). Use `<Button>` for every button (`variant`: default, outline, ghost, destructive, link); `buttonVariants()` to style a link as a button. A button's label wraps rather than pushing the page sideways when it can't fit (OD-136). The one smaller button: actions in a shopping row on a laptop look 36px tall with 14px text and a 16px icon, so the price outweighs them, with an invisible margin keeping the tap area 44px; phones keep full size (OD-82, Q54).

**Icons.** Lucide (`lucide-react`), outline, one stroke weight, always next to a text label. No icon-only buttons; no emoji as icons. On action buttons, only six get an icon (Workflow polish, Q8; OD-82, Q42; OD-99): Plus on "Add …", Check on "Mark as purchased", Pencil on Edit, Check on a phone row's "Bought" (OD-137), PanelRightOpen on "Details" (opens a side panel), ListFilter on "Filter" (OD-99), and a check on "Saved". Every icon sets `absoluteStrokeWidth`, so one weight holds at any size: 2 beside a button's or chip's semibold label (and on the dropdown chevron), 1.5 beside regular text, such as a link's ExternalLink or a back link's chevron (OD-145). The larger person icon is the one exception, at 1.5 relative. A few controls also carry an icon by convention (OD-114, Q134): X on Close, Upload on the upload box, Phone and Mail on call and email links, a plain person (CircleUserRound) beside the name on the account button and in the phone's Menu panel (OD-134), and the picture viewer's Previous/Next arrows. Every other button stays text-only, Sign out and Manage lists included. A text link that opens a new tab ends with a small ExternalLink icon (Q43). The Appearance switch is the one control drawn with icons alone (Monitor, Sun, Moon on a sliding knob): the choice's name is written beside it and every position has a screen-reader name (OD-83).

**Light and dark** are chosen under Appearance in the account menu: Device (the default, follows `prefers-color-scheme`), Light or Dark, remembered in that browser only (OD-83). The account menu is at least 320px wide, so changing Appearance doesn't resize it (OD-132, Q191). The choice is set as `data-theme` on `<html>` by a script in `index.html` before the app loads, so nothing flashes; `src/lib/theme.ts` keeps it in step afterwards. Dark tokens live under `:root[data-theme='dark']`, and Tailwind's `dark:` variant follows `data-theme`. Every new color gets a light and a dark value in `index.css`, each contrast-checked on its own (text ≥ 4.5:1, control edges and focus ≥ 3:1). Check new UI in both modes. `.ink` puts a small surface in the other theme (dark in light mode, light in dark mode); it's for things that float over the page and must stand out: the batch bar, every Undo or other message (its action is the solid button), and an active filter chip. From the keyboard, F6 moves into the messages and Ctrl+Z (Command+Z on a Mac) presses the newest Undo while focus isn't in a field; the message says so (OD-136). Inside it, use the normal tokens; they flip with it (OD-126, Q173–Q176).

**Motion** only answers something the person did (a status changing, a section opening, a save confirming, a row leaving a list). No page-load or scroll-driven animation. Reduced motion is respected globally in `index.css`: it keeps opacity fades of 150ms or less (keyframe ones too: the Saved check fades instead of growing) and drops movement, scale and blur, and the logo's stitch (Workflow polish, Q6; OD-142). Transitions name their properties (no `transition-all`). Button press is the 1px downward shift, not a scale. Tapes slide (300ms) when their number changes while you're on the page, including from zero: their fill parts are always drawn, even empty. A tape that first appears already filled doesn't move. The logo's stitch on Completed stays the one celebration (OD-131, Q188, Q190).

**Saving.** One-value edits on something that already exists save when you leave the field, with no Save button: a picture's caption, a progress photo's date and job, a room's notes and size, a job room's spec and notes, a phase's status, any status dropdown (Workflow polish, Q2). Side panels for things that exist (a shopping line, room, vendor, phase or job) are edited in place with no Save button (OD-82, OD-89); a job's room is added when ticked and taking rooms off asks first, because it removes their status and spec. In the shopping line's panel every field saves when you leave it and every dropdown when you pick, money included; a money change says what changed and offers Undo for 10 seconds (OD-82, Q37–Q53). Its purchase status is a three-way switch (To buy, Purchased, Returned) that saves on pick with Undo; Purchased takes the price as paid and Returned takes what was paid as what came back, both then editable (OD-85). Adding something, marking as purchased from a shopping row (it asks what was paid), other money (job costs, payments, estimates, the budget, which open in the side panel too, OD-90) keep a labelled button. Every save shows its state on the field's label line, right-aligned: Saving… in grey, Saved with a check in green, or Couldn't save with an alert in red, announced to screen readers; why it failed and Try again show under the field (OD-84, Q62–Q64). A control with no visible label (the panel's name heading, a status dropdown in a list row) shows its state beside it (Q66). Every error in the app, a save or a mistake to fix, is red text with an alert icon (`FormError`; Q65); an error shows under the row or control that failed, and only that row locks while it saves. A section that can't load uses `LoadError`: "Couldn't load the rooms.", why in household words (`loadProblem`, never the raw message), and Try again, which refetches only that section's queries. Every section shows loading, a load error and empty as three different states; never "No … yet" while it's still loading (`FileSection` takes the query as `source` for this; OD-110). The last save wins; there is no edit-conflict check (Q4). In an auto-saving field, Escape while typing puts back what was there (with nothing typed, Escape does what it does around it), and each save offers "Saved" with Undo for 10 seconds, which saves the old value again; money fields say what changed in their own message instead (`undo={false}`; OD-139, Q206). While the device is offline a bar under the top says so; saves wait and go when it's back, while the page stays open (`OfflineBar`).

**Batch editing.** Shopping has Select: a checkbox per row and Select all per room, then a bar pinned to the bottom with the count (and how many are hidden by search or filters) and the actions. Each batch saves in one transaction (`updateMany`, `removeMany`) and offers Undo for 10 seconds that puts every line back; Remove asks first (OD-101). While selecting, picked rows are tinted (`bg-accent`, edge to edge), a click anywhere on a row ticks it, the rows' own buttons step aside, the bar says "N items, $X selected" with actions named as verbs ("Move to room…", "Set category…", "Set job…"), and Escape leaves Select mode (OD-104); leaving it, or emptying the selection, puts focus back on Select (OD-136). The bar's first action is Mark as purchased: the picked things still to buy, each at its price, with Undo (OD-137). Removing one line from its panel matches: a red Remove, "Yes, remove / Keep", and Undo (`ConfirmRemove strong`, OD-103). `ConfirmRemove` is the app's only confirm step: asking focuses Yes, Keep returns focus to the button that asked. Rooms, jobs, archiving a vendor and budget entries use the red `strong` version, with Undo for 10 seconds wherever the API can restore the item (rooms, jobs, vendors, shopping lines). A room with lines or jobs on it can't be removed: the confirm says what's attached and how to move it, with an OK instead of Yes (OD-113).

**Shopping list.** A tape-measure strip under the heading shows bought (dark) against left to buy (the pale track, a yellow mark where it starts; OD-138), following the filters and search (OD-107). The count and total are said once, in the To buy heading; a search says what it found under the page heading (OD-137). Search, Filter and Select sit on one bar that stays pinned to the top of the screen while the list scrolls, with the store chips pinned under it (OD-144); `/` jumps to the search on a laptop. On a phone the bought/left tape is left out (the To buy heading says it) and By room / By store moves into the Filter panel, so the first item shows on the first screen (OD-144). The chips: one per store with what's left to buy there: one tap shows only that store (a phone scrolls the chips sideways, a laptop shows the busiest nine and "N more stores"). Group: By room or By store (`?group=store`), a two-way switch. Each room or store strip is one button that shows or hides it (Show / Hide; Hide all / Show all for the section); on a phone they start hidden, so the list opens as a short index, unless a search or store narrows it or there's one group; what was opened or hidden is kept for the tab (sessionStorage). Purchased and Returned are put away the same way and start hidden (OD-105, OD-108, OD-137). On a phone a row is compact (about 70px): picture, name, then the amount, store and details on one grey line, and one "Bought" button (Check icon) for things still to buy; tapping the row or its name opens Details, where receipts live. Grouped by store, a row names the room instead of repeating the store, and the product link reads "Product page" (OD-144). On a phone an editor's item panel opens read-first (picture, price and how many, status, room, store, job, Open product page) with the fields under an Edit heading (OD-144, Q214). A returned line's "Paid $X, $Y back" breaks between its parts (OD-136). A row with no picture in a list that has pictures shows a plain `bg-inset` tile, so the column never looks like a gap (OD-108; on a phone too, OD-145). A to-buy line with no price says "No price yet" in grey, and a bought one with no amount "Bought, amount not added" (`lineAmountText`); nothing with no amount is shown as $0.00, and its fields start empty, not "0.00" (OD-106, OD-145). A filter in use is a small `.ink` chip (32px look, 14px text, 44px tap area) with an X; renaming a store everywhere is a text link at the end of the Store hint, naming the store (OD-126, Q173–Q174). In the line's panel, a greyed-out Returned says why under the switch (OD-137).

**Jobs.** The chosen estimate's quote line says "From the {vendor} estimate"; its Edit opens the estimate and it has no Remove. Choosing an estimate and marking one declined offer Undo for 10 seconds; adding every room to a job asks first with the count. On a phone, Price, Paid and Still to pay are label-and-amount rows (OD-119). Under a job's title a summary strip gives its status, Still to pay with its paid-of-price tape, and the vendor with Call and Email; "How it's going" and its rooms are one panel, and the progress tape shows only once something is done; a job with no rooms has no such panel, and its status is picked in the summary strip (OD-129, Q181). An empty section on the job page (Estimates, Drawings, Paperwork, Progress photos, Spec) is one line: heading, "Not added yet" and its Add buttons (`FileSection` `emptyLine`). Each phase on the Jobs list opens with its status, Spent and "Planned, jobs and shopping" (from `phases.list`) and its jobs-done tape (OD-140, OD-143). The Jobs list says "paid" only above $0.00 (OD-120, Q148–Q149); "See all vendors" is an outline button beside "Add a job" (OD-129, Q184). Sections inside a panel are separated by a rule with more space above (mt-8, pt-6) than between a heading and its content.

**Rooms.** Under a room's heading, `BoughtTape` shows what's bought for it against what's left to buy, with both amounts, from `rooms.get` (`shopping`; OD-118). The room page runs heading, Jobs, What we're buying, Pictures, then Size and notes; without a cover the page starts with its heading (no band; OD-129, Q182), and a room with no pictures has one "Add pictures" row with a kind to pick. The Rooms list is a grid of cards, one per room: its cover, or its outline drawn to its proportions on the plan grid (`RoomOutline`, dashed when not measured), its size, what's left to buy for it (from `shoppingLines.totals`) and how its jobs are going; Change order turns it into a list to arrange (OD-140).

**Home.** The phase panel's heading says "underway" like the phase's status and adds what its jobs say ("Phase 1 is underway; no job has started yet"; OD-138), with the Phases list's "done" tape and its "See all" links together at the top. Rooms run needing someone, then in progress, then the rest; a room without a cover gets a compact tile, never an empty placeholder; names are headings. With nothing waiting, Needs you is one line under the greeting (OD-116). Over budget, the headline is "Planned spending is $X over budget.", the line under it says what it's made of (spent and planned against the budget), and Needs you lists "The plans are over budget" with See the money, so the page never says nothing needs you while it's over (OD-138, Q204).

**Money.** Money in or out is a two-way switch (Money in, Money out) with an amount that has no sign (`adjustmentFormSchema` gives it one); the button names the result ("Take $5,000.00 out") and saving shows a message with Undo for 10 seconds, as does editing one. The breakdowns run biggest first (`bySize`), end with a Total row, and each name links: a category or room to Shopping filtered to it, Jobs and Shopping to their pages, a phase to it on the Phases page (`#phase-{id}`); phases stay in their own order; By phase's two tables share column widths so the amounts line up (OD-129, Q183). The budget's notes show under the starting balance, and its panel and button both say "starting balance" (OD-121, Q151–Q153).

**Phases.** A phase's `active` status reads "Underway" and `planned` reads "Not started" everywhere, so it never clashes with the money's Planned (`PHASE_STATUS_LABEL`; the stored values are unchanged; OD-145). Beside each status is what it does to the money (`phaseMoneyEffect`: "Counts toward the budget" or "Not counted until it starts"). Changing it shows a message with Undo for 10 seconds; marking a phase complete with jobs still open says so in that message and under the phase until they're done. A phase's job count links to `/jobs?phase={id}` (the Jobs list for that phase, with "Show every phase"), and its panel lists its jobs with their status (OD-122, Q154, Q156–Q157). Each phase shows Spent and Planned, and a phase that isn't counted yet what it would leave (red when short), from `phases.list` (`money`), the same figures as Money's By phase (OD-123, Q155).

**Vendors.** Vendors are a grid of cards like business cards: name, trade, how many jobs, Details, and their phone and email as tap-to-call and email links (OD-140). Their panel puts contact first (Call and Email, then Phone and Email fields as `tel` and `email` inputs), then their jobs from `vendors.work`: each with its status, the chosen quote and what's been paid, then their open estimates (requested or received), each linking to the estimate. In the vendor picker, "Clear vendor" offers Undo for 10 seconds (OD-124, Q158–Q161).

**Manage.** Merging a category starts on an empty "Pick a category" and asks first, naming the whole consequence ("Merge Rugs into Furniture: moves 7 lines, removes Rugs."), then says it's done; there's no Undo because there's no un-merge. Opening Rename or Merge focuses its field, Escape cancels, and closing hands focus back to the button; Save is off while the name is blank. On a phone the field takes its own line. The API words a schema failure as the schema's messages (`errorFormatter` in `trpc.ts`), never raw JSON. The Appearance switch's knob is the text color with the picked icon in the page color, so the choice reads in light and dark (OD-125, Q162–Q165).

**Editing.** Multi-field edits and adding things open in the side panel (`Sheet`): from the bottom and nearly full height on a phone, from the right at about a third of the width on a laptop, with the page visible behind (Q16). Nothing swaps out a whole page to edit. Opening a panel or editor focuses its first field, except a panel that opens for reading, like a shopping line's, which focuses the panel so a phone doesn't raise its keyboard (OD-82); closing it returns focus to the control that opened it; leaving with unsaved changes asks "Discard your changes?" in the panel or form (`DiscardQuestion`), never the browser's dialog, except when closing the tab (OD-114, Q138). Status dropdowns stay usable while they save; the last pick wins (Q131). A side panel's name field shows a faint underline at rest (Q132).

**Forms.** One field per line, in every form and panel (OD-82, Q46). Short values keep a short field, about 12rem (`max-w-48`): money, how many, dates, and length, width and height (Q52). Nothing asks for an order number: lists are put in order with Change order, then Move up / Move down on each row (`MoveButtons`), and new rooms and phases go last (OD-117, Q141). An inline editor (a job room's spec) closes with Escape as well as Done, and focus goes back to its button (Q144). Every money field shows a drawn $ (`MoneyInput`, or `DollarBox` around an `AutoSaveField`; OD-106, OD-114). The exceptions are the Shopping filter bar and the status dropdowns inside list rows, which aren't forms. Dropdowns use `Select` (or `SelectChevron` on a styled one): the browser's arrow is hidden and ours sits 12px in, with 40px kept clear (Q45).

**Words on screen.** Household words, not database terms; on the shopping list things are "things" or "items", never "lines" (OD-139). A word that needs explaining gets a dotted-underlined "What's this?" (`WhatsThis`, a Base UI popover) beside it, never a help page: Planned in the money legend, phases on Phases. Editors and viewers get a one-time welcome note at the top of Home saying what they can do (`WelcomeNote`, dismissed per browser; OD-139, Q207; OD-143). Money not yet spent but expected (`committed` in the data) is "Planned" everywhere it's shown; the money rule is unchanged (OD-138, Q204). Things still to buy with no price yet are said, never shown as $0.00: the money legend adds "Plus N things with no price yet, not counted here" (linking to `/shopping?unpriced=true`, from `unpricedCount`), and group totals read "9 to buy, $5,960.00, 1 with no price" or "1 to buy, no prices yet" (`groupText`'s `unpriced`; OD-143, Q212). Words fit the role: someone who can't edit sees Home's card as "Worth knowing" with no count and no instructions, and hints to change things they can't are hidden. A picture with no caption shows no file name (OD-143). Every job row shows its status as a chip; a job with rooms adds its rooms' tape under it. Labels say what happens ("Mark as checked", "Record payment", not "Submit"). Avoid template habits: no "A · B" middle-dot strings, no "Word — fragment" labels, no "→" on buttons.

## Identity

Reparo is a tool for one house, not a generic project manager. Clear enough for someone non-technical: every action is a visible, labelled control (nothing hover-only or shortcut-only). Borrow Linear's feel (speed, calm, list → detail, instant feedback), not its look or power-user patterns. Use household words in the UI, not database terms. Design each screen for what it is: a room, a job, a phase, the money. The name is the mending charm; nod to it lightly. Chris reviews UI in the browser before it's committed.
